## A) CONTRACT (Behavioral Guarantees)

Independent of RTOS/driver/transport implementation.

### A1) Core Service Definition

- The **SERVER** provides commanded motion services (RUN/MOVE/GOTO/HOLD/STOP)
  within configured limits, enforces safety invariants (E-STOP latch +
  watchdog), and reports "truth" via telemetry and fault events.
- The **CLIENT** requests intent and consumes telemetry/faults; it must not
  depend on motor-driver registers, SPI details, or RTOS internals.

### A2) Safety Invariants (MUST HOLD)

**1) E-STOP LATCH**
- On ESTOP (client command or server-detected fault), outputs are disabled
  immediately and a latch is set.
- While latched, all motion/enable commands are rejected.
- Latch clears only via explicit reset/clear procedure and only if fault
  condition is not present.

**2) WATCHDOG / COMMS LOSS**
- Server requires periodic heartbeat. If not received within timeout, server
  enters safe stop and latches fault.
- Server continues to report status when possible.

**3) FAULT PROPAGATION**
- Server must report fault reason flags to client.
- Client may propagate a global stop to other controllers.

### A3) Motion Semantics (MUST BE DEFINED)

- **Units**: server defines canonical units (steps, steps/s, RPM, ticks).
  Client and server must agree.
- **Ordering**: commands are executed in arrival order unless SYNC queue is used.
- **Stop semantics**:
  - SOFT stop: decelerate using configured DECEL
  - HARD stop: immediate stop (driver stop / disable policy)
- **Hold semantics**:
  - HOLD means "actively resist motion" (closed-loop uses encoder if enabled;
    otherwise stepper hold current).

### A4) Synchronization Semantics (Multi-Controller)

Support at least one of:
- `START_AT <tick>` (time-tagged execution on server monotonic tick), or
- PREPARE/COMMIT (two-phase) — the current model: QUEUE + ARM + START/START_AT

**Guarantees:**
- Armed commands begin simultaneously at START or at specified START_AT tick.
- Server exposes tick and timing probes to measure coordination quality.

### A5) Effort/Torque Limit Semantics (Safety Envelope)

- Client may specify an effort limit per motion (normalized 0..1 or current
  limit A).
- Server enforces the effort envelope (implemented as coil current limit
  and/or stall policy).
- Server may estimate torque and report margin/saturation, but does not
  guarantee exact Nm without a sensor.

### A6) Observability (Non-intrusive)

- Server supports status snapshot and timing probes.
- Server SHOULD implement transaction trace ring buffer (optional command to
  dump).
- Debug/bypass commands exist but are NOT part of stable contract; they
  require explicit unlock.

### A7) Portability / Loose Coupling (Explicit Goal)

- **Transport agnostic**: UART/USB/CAN all valid. Protocol defines framing;
  do not assume USB packet boundaries.
- **Scheduling agnostic** inside server: FreeRTOS vs super-loop should not
  change external behavior/contract.
- **Driver agnostic**: PowerSTEP01 may be replaced; stable commands remain.

## B) SCPI-LIKE COMMAND SET

Consolidated, with Namespaces + Backward-Compatible Aliases.

### B0) Conventions

- Line-based ASCII: `<CMD> [args...] \r\n`
- Responses:
  - `OK [data]\n`
  - `ERROR <code> [msg]\n`
  - Optional JSON mode: `{"status":"ok|error", ...}\n`
- Wheel addressing: 1 controller per wheel (no channel selection needed)
- Sequence numbers (optional): `@<seq> <CMD> ...` / `OK @<seq> ...`

### B1) Identity / Version

| SCPI Command | Description |
|---|---|
| `*IDN?` | `<vendor>,<product>,<fw_ver>,<build>` |
| `SYST:VER?` | `<fw_ver> <build_date> <git_hash>` |
| `DEV:ID?` | Query device ID |
| `DEV:ID <id>` | Set device ID |
| `DEV:ROLE?` | Query role (`FL`/`FR`/`RL`/`RR`/`NONE`) |
| `DEV:ROLE <role>` | Set role |

**Aliases**: `GET_DEVICE_ID` → `DEV:ID?`, `SET_DEVICE_ID` → `DEV:ID`,
`SET_ROLE` → `DEV:ROLE`, `VER`/`VERSION` → `SYST:VER?`

### B2) Mode / Encoder

| SCPI Command | Description |
|---|---|
| `CTRL:MODE?` | Query control mode (`OPEN_LOOP`/`CLOSED_LOOP`) |
| `CTRL:MODE <mode>` | Set control mode |
| `CTRL:ENC:STAT?` | Encoder availability/status |

**Aliases**: `GET_MODE` → `CTRL:MODE?`, `SET_MODE` → `CTRL:MODE`,
`GET_ENCODER_STATUS` → `CTRL:ENC:STAT?`

| SCPI Command | Description |
|---|---|
| `SYST:TICK?` | Query FreeRTOS tick counter |

## C1: Does the contract cleanly separate stable service from driver bring-up?

**Verdict: Yes, with one boundary that needs sharpening.**

The `DBG:*` / `DRV:PS01:*` namespace with unlock/lock is the right approach.
The current firmware has ~20 debug commands (`SPI_DEBUG`, `SPI_BITBANG`,
`PS01_DIAG`, `GPIO_DUMP`, etc.) that are freely accessible alongside motion
commands in a flat `strcmp` dispatch. The proposal correctly quarantines these.

The sharpening needed is the **MCONFIG boundary**. Currently `MCONFIG_KVAL`,
`MCONFIG_OCD`, `MCONFIG_STALL`, etc. directly set powerSTEP01 register values
(raw `uint8_t` KVAL 0x00-0xFF, raw OCD threshold 0-31). These are
driver-specific knobs. The proposal handles this correctly by:

- Exposing behavior through stable abstractions: `MOT:CFG:EFFORT:LIMIT` (0..1
  normalized), `MOT:CFG:STALL:POL` (STOP/ESTOP/RETRY)
- Relegating raw register access to `DRV:PS01:*` (unstable)

This is the right split. The stable API says *what* the client wants (effort
limit, stall policy). The server translates to driver-specific registers
internally. If you replace the powerSTEP01 with a TMC5160 tomorrow, the
stable commands survive; only `DRV:*` changes.

**One concern**: `MCONFIG_SAVE` / `MCONFIG_LOAD` / `MCONFIG_RESET` operate on
the flash-persistent config (`motor_config.hpp`). These are behavioral (the
client wants "remember these settings across reboots") not driver-specific.
They should probably live in the stable namespace:

```
MOT:CFG:SAVE     -> persist current config
MOT:CFG:LOAD     -> reload from flash
MOT:CFG:RESET    -> factory defaults
MOT:CFG?         -> show current config
```

With the raw register access (`MCONFIG_KVAL <hold> <run> <acc> <dec>`) moved
to `DRV:PS01:KVAL`.

## C2: Are the safety invariants and reset semantics strong enough?

**Verdict: Mostly yes. Three gaps identified.**

### What's solid

The E-STOP latch model is correctly implemented. From `command_queue.hpp`:

```
IDLE -> ARMED -> RUNNING -> IDLE
         |                    |
   CLEAR_QUEUE <---------+
         |
         v
       ESTOP/FAULT (any state -> ESTOP via emergencyStop())
         |
       clearFault() -> IDLE  (only from FAULT/ESTOP)
```

`emergencyStop()` in `CommandQueue` sends HardStop to motor, clears the queue,
and latches ESTOP state. `clearFault()` only works from FAULT/ESTOP → IDLE.
Motion commands are rejected in FAULT/ESTOP. This is sound.

The comms watchdog (`comms_task.cpp:135-141`) fires `emergencyStop()` on
heartbeat timeout, latches `s_commsTimedOut`, and `CLEAR_FAULT` clears both
the motor fault and comms timeout. This is also sound.

### Gap 1: No explicit power-on state specification

The proposal says nothing about what state the server starts in. Currently:
firmware boots → inits → IDLE state, motor outputs in HiZ (high impedance,
no current). This is correct and safe. The contract should state:

> On power-on or reset, the server SHALL enter IDLE state with outputs
> disabled (HiZ). The watchdog SHALL be disabled. The client must explicitly
> enable heartbeat and enable motor outputs.

### Gap 2: CLEAR_FAULT should verify the underlying condition is gone

Currently `cmdClearFault()` unconditionally clears:

```cpp
Services::QueueResult result = Services::g_commandQueue.clearFault();
if (result == Services::QueueResult::OK) {
    Tasks::CommsTask_ClearCommsTimeout();
    respondOk("IDLE");
}
```

It does NOT check whether the powerSTEP01 STATUS register still shows a fault
(OCD, thermal, UVLO). If the motor driver is still in fault, clearing the
latch and returning to IDLE allows the client to immediately issue motion
commands that will fail again.

**Recommendation**: Before clearing, read STATUS. If hardware fault flags are
still active, return `ERROR FAULT_STILL_ACTIVE <flags>`. The client must
resolve the hardware condition first. The proposal's `SYST:FAULT:CLEAR`
description says "only if safe; else ERROR" — this is the right intent, but
the firmware doesn't currently enforce it.

### Gap 3: Comms watchdog and motor fault are conflated

`CLEAR_FAULT` clears BOTH the motor ESTOP latch AND the comms timeout in one
shot. These are different failure modes:

- Motor fault (OCD, stall) = hardware protection triggered
- Comms timeout = client disappeared

The proposal's `SYST:FAULT:STAT?` returning flags is the right direction.
Consider making the clear operation targeted:

```
SYST:FAULT:CLEAR           -> clear all (current behavior)
SYST:FAULT:CLEAR COMMS     -> clear only comms timeout
SYST:FAULT:CLEAR MOTOR     -> clear only motor fault
```

Or at minimum, `SYST:FAULT:STAT?` should return which fault type is latched
so the client can diagnose before clearing.

## C3: Is the SYNC model sufficient for 4-wheel coordination?

**Verdict: Sufficient for the current use case, with one known limitation.**

### What works

The QUEUE/ARM/START model is sound for the primary use case: "tell all 4
wheels what to do, then trigger them simultaneously."

```
Pi sends to each STM32:          STM32_FL    STM32_FR    STM32_RL    STM32_RR
  QUEUE RUN 1000 1                  queued      queued      queued      queued
  ARM                               armed       armed       armed       armed
  START_AT 500000                   waiting     waiting     waiting     waiting
                                    ...tick 500000...
                                    all start simultaneously (within ~1ms jitter)
```

The tick-based synchronization works if the Pi first probes each controller's
tick offset via `PING`. At 1000 Hz FreeRTOS tick, the resolution is 1ms. For
stepper motors starting/stopping together, 1ms jitter is likely acceptable.

### The known limitation: mid-motion velocity profiling

For complex trajectories (curved paths, acceleration profiles), the Pi would
need to stream incremental `RUN <speed>` commands at regular intervals to each
wheel. The current architecture supports this (commands go through the worker
thread → UART → CommsTask → MotorTask queue), but:

1. The 10ms CommsTask poll adds jitter to each update (addressed in the forum
   as P0 fix)
2. Streaming 4 wheels × 50 Hz velocity updates = 200 commands/sec total. At
   ~20 chars per command + response, that's ~4000 chars/sec per port — well
   within 115200 baud capacity (11520 chars/sec).
3. The worker thread serialization means commands to different wheels can't
   truly be simultaneous. This is fine if each wheel has its own UART (the
   planned 4-controller architecture), but would be a problem if sharing a bus.

### Missing: SYNC:STATUS?

The proposal doesn't include a way to query the sync state machine. Add:

```
SYNC:STAT?   -> OK <state> <queue_depth> <armed_tick>
```

This lets the Pi verify all 4 controllers are in ARMED state before issuing
START_AT.

## C4: Is the effort/torque limit approach acceptable on STM32/PowerSTEP01?

**Verdict: Acceptable with constraints. Start with persistent limit only.**

### What the hardware actually provides

The powerSTEP01 in **voltage mode** (which is what we're using — no current
sense resistors on the X-NUCLEO-IHM03A1) provides:

- **KVAL registers** (HOLD/RUN/ACC/DEC): 0-255, controls PWM duty cycle
  which is proportional to voltage applied to coils. In voltage mode,
  voltage ≈ current × winding resistance, so KVAL is roughly proportional
  to current/torque at low speeds. At higher speeds, back-EMF reduces the
  effective current.

- **OCD threshold**: Overcurrent detection (0-31, ~375mA steps). This is a
  safety cutoff, not a precision current limit. It fires and latches a fault.

- **Stall threshold**: Back-EMF based stall detection (0-127). Detects when
  the motor loses synchronization. Also a safety mechanism.

There is **no** precision current measurement. The powerSTEP01 CAN operate in
current mode with external sense resistors, but the IHM03A1 board doesn't
have them.

### What `MOT:CFG:EFFORT:LIMIT <x>` can realistically do

Map normalized effort (0.0 to 1.0) to KVAL_RUN scaling:

```
KVAL_RUN = round(effort * max_kval)   // max_kval from config (default 0xFF)
KVAL_ACC = same or configured ratio
KVAL_DEC = same or configured ratio
KVAL_HOLD = separate hold ratio
```

This is a coarse but useful control. `EFFORT:LIMIT 0.5` means "use half the
configured maximum voltage." For a stepper motor, this roughly halves the
available torque (at low speed, ignoring back-EMF).

### What `MOT:CFG:STALL:POL` can do

Currently `motor_config.hpp` has `faultAction`: 0=HardStop, 1=HardHiZ,
2=SoftStop. The proposal's `STOP/ESTOP/RETRY` maps to:

- STOP → faultAction=0 (HardStop, maintain position)
- ESTOP → latch fault, disable outputs
- RETRY → not currently implemented, would require automatic recovery logic

**Recommendation**: STOP and ESTOP are straightforward. Skip RETRY for now —
automatic stall recovery is complex (requires current reduction + re-sync
attempt) and dangerous if the stall was caused by a physical obstruction.

### Per-motion vs persistent effort limit

The proposal shows `MOT:MOVE <steps> <dir> [eff]` with per-motion override.
This requires:

1. Read current KVAL registers
2. Compute new KVAL from effort
3. Write KVAL registers (4 SPI transactions)
4. Execute motion command
5. Restore original KVAL after motion completes

Steps 3-5 must be atomic from the motor's perspective (can't change KVAL
mid-motion). The MotorTask processes commands sequentially, so this is doable
but adds 4 SPI register writes per motion command (~64µs bit-bang overhead).

**Recommendation**: Start with persistent-only effort limit
(`MOT:CFG:EFFORT:LIMIT`). Per-motion override is premature complexity. The Pi
can always change the persistent limit between motions if needed.

## C5: Are the SCPI namespaces + aliases a good migration path?

**Verdict: Yes. The migration path is sound. A few parser concerns to address.**

### Why this works

1. **Backward compatibility**: Every existing flat command (`MOVE`, `STOP`,
   `GET_STATUS`) continues to work as an alias. No client code breaks.

2. **SCPI familiarity**: Engineers who've used oscilloscopes, signal
   generators, or any GPIB instrument will recognize `MOT:CFG:ACCEL` and
   `SYST:FAULT:CLEAR` immediately.

3. **Namespace prevents collision**: As the command set grows (effort limits,
   telemetry streaming, PID tuning, etc.), flat names like `SET_LIMIT` become
   ambiguous. `MOT:CFG:EFFORT:LIMIT` vs `SYST:HB:TIMEOUT` are unambiguous.

4. **Conciseness**: Many SCPI names are actually shorter than the current
   flat names: `SYST:HB` < `HEARTBEAT`, `FMT` < `SET_FORMAT`,
   `MOT:EN` < `ENABLE`.

### Parser implementation concerns

The current parser tokenizes on whitespace only and matches the first token
via `strcmp`. The SCPI names (e.g., `MOT:MOVE`) contain `:` which is NOT
whitespace, so `MOT:MOVE 1000 1` would parse as:

```
cmd = "MOT:MOVE"  (single token, uppercased)
args[0] = "1000"
args[1] = "1"
```

This works with the existing parser. `strcmp(cmd.cmd, "MOT:MOVE")` is valid.
No tokenizer changes needed for the colon. The `toupper()` loop in `parse()`
already handles this since `:` is not alphabetic.

**However**: the `cmd.cmd` field is only 16 chars. `SYST:HB:STAT?` is 14
chars — fits. `UI:DISP:BITMAP:B64` is 19 chars — **does not fit**. Either:

1. Increase `cmd.cmd` to 24 chars (costs 8 bytes of stack per parse), or
2. Keep the long names as aliases only (use short stable names as primary):
   `UI:DISP:BMP64` (14 chars, fits)

**Recommendation**: Increase `cmd.cmd` to 24. The stack cost is negligible
(parse is called once per command) and it future-proofs the namespace.

### The `?` suffix convention

SCPI uses `CMD?` for queries. The current firmware uses `GET_*` prefix.
Supporting both is trivial — just add aliases:

```
strcmp(cmd.cmd, "SYST:TICK?") == 0   // SCPI query
strcmp(cmd.cmd, "GET_TICK") == 0     // legacy alias
```

The `?` is a valid printable character (ASCII 63), already handled by the
parser's `byte >= 32 && byte < 127` check.

### The `*` prefix (IEEE 488.2)

`*IDN?` requires `*` to be accepted as part of a command token. The parser's
character range already includes `*` (ASCII 42). Works without changes.

### Dispatch strategy for ~65+ entries

The current `if/else if` chain of ~65 `strcmp` calls is O(n) per command.
With aliases doubling the entries to ~130, this becomes noticeable (though
still fast in absolute terms — ~130 × strcmp at ~20 chars ≈ ~50µs worst case
on a 84 MHz Cortex-M4).

Options:
1. **Keep linear scan** — simple, fast enough, works now. Revisit if profile
   shows it matters.
2. **Namespace prefix dispatch** — parse the first token before `:`, use a
   small switch/table to select namespace handler, then `strcmp` within
   namespace. Reduces comparisons by ~5x.
3. **Perfect hash** — tools like `gperf` generate perfect hash functions for
   known command sets. Zero-collision O(1) lookup. Overkill for now.

**Recommendation**: Option 2 (namespace prefix dispatch) is the sweet spot.
It's a natural fit for the SCPI hierarchy and reduces dispatch cost as the
command set grows.

## Additional Gaps and Suggestions

### Gap 6: No unsolicited event model

The proposal mentions "fault propagation" in A2 but doesn't define how the
server notifies the client of asynchronous events. Currently the firmware has:

- `EVENT JOY <direction> <pressed|released>` — joystick events in REMOTE mode

But there is NO async notification for:
- Motor stall detected
- OCD triggered
- Watchdog about to fire
- Motion complete (RUNNING → IDLE transition)

The client discovers these by polling `GET_STATUS` every 500ms. For a safety
system, detecting a stall 500ms after it happens is not ideal.

**Suggestion**: Add an event prefix model:

```
!FAULT <flags> <tick>           (unsolicited fault notification)
!MOTION:COMPLETE <tick>         (motion finished)
!STALL <bridge> <tick>          (stall detected)
!COMMS:WARNING <remaining_ms>   (watchdog approaching timeout)
```

Client protocol layer must handle `!` prefix lines as events, not command
responses. This is a common pattern in instrument protocols.

### Gap 7: No protocol version negotiation

`*IDN?` returns firmware version. But if the protocol changes (new commands,
changed semantics), the client needs to know which protocol version the
server speaks. Add:

```
SYST:VER:PROTO?   -> OK 2   (protocol version number)
```

The client checks this on connect and adapts its command set. This is
especially important for the multi-controller case where wheels might have
different firmware versions.

### Gap 8: Encoder not in stable namespace

The proposal has `CTRL:ENC:STAT?` for encoder status but no stable command
for encoder telemetry (position, velocity, index). Currently `ENCODER`/`ENC`
provides this, and it's included in `GET_STATUS`. Add:

```
CTRL:ENC?   -> OK <count> <velocity> <index_seen> <index_tick>
```

Or just rely on `DIAG:STAT?` which already includes encoder data. But a
lightweight encoder-only query is useful for closed-loop tuning.

### Gap 9: `MOT:HOLD` is redundant with `MOT:EN`

In stepper motor context, "hold" means "apply holding current." This is the
default state after `STOP` — the powerSTEP01 applies KVAL_HOLD automatically.
`MOT:HOLD` would be equivalent to "stop + ensure outputs enabled" which is
what `MOT:STOP` + `MOT:EN` already achieves.

Unless `HOLD` means something specific for closed-loop mode (e.g., "actively
servo to current position using encoder feedback"), it's redundant. Defer
until closed-loop is implemented.

### Gap 10: Missing telemetry streaming command

you add `Services::Motion::goTo(int32_t pos)`, you must also add
`TracedMotionService::goTo(int32_t pos)` that calls the trace macro then
forwards. Two files to update for every API change. During active development
(which this is — we're adding SCPI commands, effort limits, stall policies),
this doubles the surface area of every change.

**What I insist on instead:**

```cpp
// trace.hpp — the entire trace infrastructure
#define TRACE_ENTRY(name, ...) TraceRing::record(TraceDir::ENTRY, name, __VA_ARGS__)
#define TRACE_EXIT(name, result) TraceRing::record(TraceDir::EXIT, name, result)

class TraceRing {
public:
    static void record(TraceDir dir, const char* name, uint32_t arg0 = 0,
                       uint32_t arg1 = 0);
    static size_t dump(char* buf, size_t bufLen);  // for DBG:TRACE:DUMP
private:
    static TraceEntry s_ring[TRACE_RING_SIZE];     // statically allocated
    static volatile size_t s_head;
};
```

Usage at each boundary:

```cpp
// In motion_service.cpp
Result Motion::run(uint32_t speed, bool forward) {
    TRACE_ENTRY("MOT:RUN", speed, forward);
    MotorCommand cmd = {};
    cmd.type = MotorCmdType::Run;
    cmd.param1 = static_cast<int32_t>(speed);
    cmd.param2 = forward ? 1 : 0;
    auto ok = Tasks::MotorTask_SendCommand(cmd);
    auto result = ok ? Result::OK : Result::QUEUE_FULL;
    TRACE_EXIT("MOT:RUN", static_cast<uint32_t>(result));
    return result;
}
```

One file per service. Trace is two lines per function. No wrapper class. No
interface duplication. The ring buffer is a fixed-size static array — no heap,
constant-time, ISR-safe if needed.

### 3. Service count: 3, not 5. And ConfigService earns its keep.

The 11:00:54 entry says "MotionService + SafetyService" for Phase 3. I agree
these two are mandatory. But I insist on a third: **ConfigService**.

Why: the parser currently calls into THREE separate globals for configuration:

```
Services::g_motorConfig.getConfig()         // KVAL, motion params, fault flags
Services::g_deviceConfig.getDeviceId()      // identity
Services::g_controlMode.getMode()           // open-loop vs closed-loop
```

Plus it will soon need `MOT:CFG:EFFORT:LIMIT` (maps to KVAL scaling) and
the proposed unit conversions for ACC/DEC (steps/s² ↔ raw register). These
are all "read/write a persistent setting, optionally save to flash."

Leaving these scattered across 3 globals while extracting Motion and Safety
into clean service interfaces creates an inconsistency: some parser calls go
through service APIs, others still poke globals directly. ConfigService
unifies them:

```cpp
namespace Services::Config {
    // Motor parameters
    Result setAcceleration(float stepsPerSecSq);  // converts to raw internally
    Result setDeceleration(float stepsPerSecSq);
    Result setMaxSpeed(float stepsPerSec);
    Result setEffortLimit(float normalized_0_1);   // maps to KVAL
    // Identity
    Result setDeviceId(uint16_t id);
    uint16_t getDeviceId();
    // Persistence
    Result save();    // flash write
    Result load();    // flash read
    Result reset();   // factory defaults
}
```

This is where the ACC/DEC unit conversion lives. This is where the effort
abstraction lives. This is where `MCONFIG_SAVE` / `MCONFIG_LOAD` graduate
from driver-specific commands to stable contract operations. Deferring this
to "Phase 5" means the unit conversion gap (identified in my ~11:00 entry)
stays open through the entire SCPI migration — the client sends raw register
values through supposedly-stable `MOT:CFG:ACCEL` commands. That's the
contract violation we agreed needs fixing.

## Agreed plan (final, with mechanism decisions)

| Phase | Deliverable | Mechanism |
|---|---|---|
| **1** | Parser infra + SCPI aliases | Widen `cmd.cmd` to 24. Namespace prefix dispatch. Add ~60 SCPI entries as primary, keep ~60 flat names as aliases. No behavior change. |
| **2** | Safety hardening | Read STATUS register in `cmdClearFault()` before clearing. Reject if hardware fault active. Document power-on state: IDLE + HiZ + watchdog disabled. |
| **3** | Service extraction | Create `Services::Motion`, `Services::Safety`, `Services::Config` as namespace free-function APIs with result enums. Parser calls services only. No vtable. |
| **4** | Trace infrastructure | Static ring buffer + `TRACE_ENTRY`/`TRACE_EXIT` macros. Instrument service boundary functions. `DBG:TRACE:DUMP` command. Selective: Motion + Safety + Transport only. |
| **5** | Deferred | Async events (`!FAULT`), telemetry streaming, driver swap abstraction, broader tracing. |

## Strengths of this consensus

1. **Delivers external value first** (Phase 1) — Pi integration unblocked
2. **Safety before refactoring** (Phase 2) — fault-clear is safe before we
   restructure the code that calls it
3. **Minimal viable layering** (Phase 3) — 3 services, not 5; free functions,
   not virtual; fixes the coupling without over-engineering
4. **Tracing is additive** (Phase 4) — macros at call sites, added after
   services exist, no wrapper classes to maintain
5. **Each phase is independently shippable** — if we stop after Phase 2, the
   system is better than today. If we stop after Phase 3, the architecture is
   clean. Phase 4-5 are pure improvements on a stable base.

## Open question for the architect

One decision remains that only the system architect can make:

**Should Phase 3's ConfigService include the ACC/DEC unit conversion
(steps/s² ↔ raw register) immediately, or defer it?**

If yes: `MOT:CFG:ACCEL 1000` means 1000 steps/s² from day one. Clean
contract. But it changes behavior — the firmware currently accepts raw 12-bit
values (1-4095) and the existing `ACCEL` alias would need to decide: does
`ACCEL 100` mean 100 steps/s² (new) or raw register value 100 (legacy)?

If no: `MOT:CFG:ACCEL` accepts raw values just like `ACCEL` does today. The
unit conversion comes in Phase 5. The contract is slightly impure but nothing
breaks.

I recommend yes — do it in Phase 3. The SCPI name `MOT:CFG:ACCEL` is new, so
it has no legacy baggage. The flat alias `ACCEL` keeps its current raw-value
behavior for backward compatibility. The client chooses which to use.
