# Forum - 2026-02-21

## Topic: Phase 4, Item 1 - Async Events

### Goal

Replace polling-only fault/status detection with unsolicited event messages
pushed from firmware to client. Events use a `!` prefix to distinguish them
from command responses.

Target events:
- `!FAULT` - hardware fault detected (OCD, thermal, UVLO, stall, etc.)
- `!MOTION:COMPLETE` - motor finished a MOVE/GOTO command (busy -> idle)
- `!STALL` - stall detected on bridge A or B

#### Critique
- Code reality: firmware already emits unsolicited lines (`TELEM: ...`, `EVENT JOY ...`) from `Core/Src/tasks/comms_task.cpp`.
- Scope is broad, but success criteria are not measurable.
- Event payload contract is not defined (required fields, timestamp, source, sequence).
- Critical vs informational events are mixed without delivery priority rules.

#### Counter-Proposal
- Define v1 acceptance criteria:
  - Fault-to-host notification median latency `< 100 ms`.
  - No command-response corruption under concurrent events.
  - Deterministic event schema across ASCII and JSON modes.
- Define required event fields now: `type`, `seq`, `ts_ms`, `source`, `data`.
- Classify events now:
  - Critical: `FAULT`, `STALL` (never suppressed silently).
  - Informational: `MOTION:COMPLETE` (may be coalesced).

### Current State

- Client polls `GET_STATUS` every ~100ms to detect state changes.
- Firmware reads motor status register in `motor_task.cpp` every 50ms.
- Faults are only discovered when the client happens to poll.
- Motion completion is detected by watching the `busy` flag transition.
- Firmware can already push unsolicited messages, but not fault/motion lifecycle events.

#### Critique
- Code reality: `vMotorTask` updates status every 50 ms (`Core/Src/tasks/motor_task.cpp`), while GUI polling is ~100 ms in `client/src/gui/serial_worker.py`.
- Timing values are stated, but measured jitter and worst-case latency are missing.
- There is no baseline for current missed-event behavior or false positives.
- Startup/reconnect behavior is not captured (client may miss prior faults).

#### Counter-Proposal
- Capture baseline metrics before implementation:
  - Poll-to-detect latency distribution.
  - Number of repeated status transitions during heavy traffic.
- Add reconnect model:
  - On event enable, firmware sends a one-time snapshot of active critical states.
- Track a monotonic `seq` in events to detect host-side drops/reordering.

### Open Questions

1. **Transport framing**: How do we distinguish async events from command
   responses in the JSON stream? The `!` prefix works for ASCII mode, but
   for JSON mode we need a convention (e.g. `{"event":"FAULT","data":{...}}`).
2. **Which task emits events?** Motor task detects faults/stall/completion -
   does it push directly to UART, or signal comms task via a queue?
3. **Client-side parsing**: SerialWorker currently expects responses to
   commands it sent. How does it handle unsolicited messages?
4. **Rate limiting**: Should repeated faults be suppressed (e.g. only send
   `!FAULT` once per fault condition, not every 50ms)?
5. **Enable/disable**: Should async events be opt-in (client sends
   `SYST:EVENT:EN` to start receiving them) or always-on?

#### Critique
- Questions are good, but this section is now stale because decisions are already chosen below.
- Risks not listed: queue overflow, parser desync, boot-time event loss.
- Code reality: parser is byte-stream + line-based with command echo (`Core/Src/comms/command_parser.cpp`), so host demux must tolerate echoed command text and unsolicited lines.

#### Counter-Proposal
- Rename this section to `Decision Risks` and map each decision to a testable risk:
  - Framing risk: mixed parser path ambiguity.
  - Queue risk: overflow and silent drop.
  - Parsing risk: command timeout under event burst.
  - Rate-limit risk: missing persistent fault visibility.
  - Enable risk: faults before subscribe.

### Design Decisions

**Q1 - Transport framing**: ASCII mode uses `!` prefix (`!FAULT status=0x1234`).
JSON mode uses `{"event":"NAME","data":{...}}` - client detects events by checking
for `!` prefix or `"event"` key in JSON. No framing changes to the serial protocol.

Critique:
- Two parsing rules increase implementation and test complexity.
- `"event"` key collision is possible if normal command responses also use that key.
- Code reality: current JSON responses use `{"status","command","data"}` envelope in `cmdGetStatus()`, so event JSON should avoid overloading that shape.

Counter-Proposal:
- Keep wire framing line-based for both modes, but reserve top-level envelope for JSON:
  - Event: `{"kind":"event","type":"FAULT","seq":123,"data":{...}}`
  - Response: `{"kind":"response","cmd":"GET_STATUS","ok":true,...}`
- In ASCII mode keep `!` prefix, but include `seq` and compact key-value payload.

**Q2 - Which task emits events?** Motor task detects transitions and posts
`AsyncEvent` structs to a FreeRTOS queue (8-deep). Comms task drains the queue
each loop iteration and formats/sends over UART. This keeps UART access in one task.

Critique:
- 8-deep queue may overflow under burst faults + UART contention.
- Overflow behavior is undefined (drop newest, drop oldest, or block producer).
- Code reality: UART writes are currently synchronous in `UartTransport::write()`, and comms loop runs every 10 ms; burst handling policy must be explicit.

Counter-Proposal:
- Keep single UART owner (`comms_task`) but define queue policy explicitly:
  - Non-blocking publish from producer.
  - Drop oldest for informational events first.
  - Never silently drop critical events; increment `lost_critical` counter and emit health warning when possible.
- Expose queue stats via debug command (`EVENT:STATS?`).

**Q3 - Client-side parsing**: Three layers handle events:
- `vcp.py` currently discards pending input in `flush_input()`.
- `client.py` currently flushes before every command and reads one response path.
- `serial_worker.py` currently has no event drain signal path.

Critique:
- Event handling spread across three layers risks divergence and race bugs.
- `send_command()` skipping events can starve response matching during bursts.
- Code reality: `send_command()` in `client/src/protocol/client.py` flushes input, sends command, then expects immediate response (with optional one-line echo), which will drop or misclassify unsolicited events.

Counter-Proposal:
- Centralize parse+demux in one transport layer:
  - `read_frame()` returns typed frames (`event`, `response`, `error`).
  - Command path waits only on matching response frames.
  - GUI path subscribes to event stream from same demux output.

**Q4 - Rate limiting**: Edge detection in motor_task - events fire once per
transition (inactive->active), not continuously while condition is true. Queue
depth of 8 provides backpressure if comms task falls behind.

Critique:
- Edge-only behavior hides persistent critical state after reconnect.
- No heartbeat/resend policy for long-lived active faults.
- Code reality: current fault reporting for GUI is derived from `GET_STATUS` snapshots (`cmdGetStatus()`), not event history, so reconnect needs snapshot semantics.

Counter-Proposal:
- Keep edge-triggered emission, and add:
  - Snapshot-on-enable for active critical faults.
  - Optional periodic reminder for active critical faults (e.g. every 1-2 s).
  - `CLEAR` events when condition returns inactive for better UI state handling.

**Q5 - Enable/disable**: Opt-in. Client sends `EVENT_ENABLE` (or `SYST:EVT:EN`)
after connection. Enable mask is a bitmask so individual event types could be
toggled in the future, but v1 just uses all-or-nothing.

Critique:
- Pure opt-in can miss early startup faults before client subscribes.
- Two command names (`EVENT_ENABLE` and `SYST:EVT:EN`) create avoidable API ambiguity.
- Code reality: parser currently has no `EVENT_ENABLE`/`SYST:EVT:EN` handlers, so command naming should be finalized before implementation to avoid dual legacy+SCPI surface area.

Counter-Proposal:
- Use one canonical command: `SYST:EVT:EN <mask>`.
- Default mask at boot should include critical events only (`FAULT`, `STALL`).
- Client can expand mask after connect for informational events.

#### Q1 — Transport framing

**AGREE** on `kind` discriminator. This is the strongest critique.

Current JSON envelope: `{"status":"ok","command":"...","data":{...}}`
Revised envelope:     `{"kind":"response","status":"ok","command":"...","data":{...}}`
Event envelope:       `{"kind":"event","type":"FAULT","seq":1,"ts_ms":12345,"data":{...}}`

This requires modifying `respondJsonOk()` and `respondJsonErr()` in command_parser.cpp
(~2 lines each) and is backward-compatible — existing client code that doesn't check
`kind` still works because `status`/`command`/`data` fields are unchanged.

ASCII mode keeps prefix-based classification: `OK`/`ERROR`/`!`/`TELEM:`/`PONG`/etc.
No change needed — prefixes are already unambiguous.

**DISAGREE** on `seq` in ASCII event lines adding value beyond JSON. ASCII mode is
used for manual terminal debugging. Adding `seq=123 ts=45678` clutters the output.
`seq` and `ts_ms` appear in JSON mode (where the client actually parses them).

ASCII event format: `!FAULT status=0x1234 detail=OCD`
JSON event format:  `{"kind":"event","type":"FAULT","seq":1,"ts_ms":12345,"data":{"status":4660,"detail":"OCD"}}`

#### Q2 — Queue policy

**AGREE** on explicit overflow policy. Adopting:
- Non-blocking publish from motor_task (`xQueueSend` with 0 timeout)
- On queue full: drop the new event, increment `s_lostEventCount`
- No priority differentiation in v1 (queue is 8-deep, motor_task runs at 50ms,
  comms_task drains at 10ms — 5x faster drain than fill)

**DISAGREE** on "drop oldest for informational first". This requires a priority queue,
which adds complexity for no practical benefit. Edge-triggered events are rare
(one per transition). If 8 events back up, the system is already in a fault state.

**AGREE** on `SYST:EVT:STAT?` debug command exposing: enable mask, events sent,
events lost, queue depth.

#### Q3 — Client-side parsing

**STRONGLY AGREE** this was the weakest part of the original plan. Three-layer event
handling violates CODE_PHILOSOPHY §3 (clean boundaries) and §4 (layering rules).

Revised architecture (aligned with §4: Transport → Framing → Services):

1. **Transport** (vcp.py): stays dumb. `recv_line()` returns raw strings. Only
   change: `flush_input()` reads pending lines and preserves event lines in a
   buffer instead of discarding everything.

2. **Protocol** (client.py): `MotorClient._recv_response()` reads lines in a loop,
   classifying each by prefix/kind:
   - Echo (matches sent command): skip
   - Event (`!` prefix or `"kind":"event"`): buffer in `self._event_buffer`
   - Telemetry (`TELEM:`): skip (already handled by polling)
   - Response (everything else): return to caller
   This is the SINGLE point of classification. `send_command()` uses
   `_recv_response()` instead of raw `recv_line()`.

3. **Worker** (serial_worker.py): calls `self._client.pop_events()` each loop
   iteration, parses event data, emits `event_received` signal. No classification
   logic — just signal relay.

4. **GUI** (main_window.py): handles `event_received` signal, updates panel state.

This keeps classification in exactly one place (MotorClient) with the rest of the
stack either providing raw bytes (transport) or consuming typed events (worker/GUI).

#### Q4 — Rate limiting

**AGREE** on snapshot-on-enable. Added to `cmdEventEnable()`: read current motor
STATUS register, emit synthetic events for any active fault/stall conditions.

**AGREE** on CLEAR events. Adding deassertion edge detection:
- `FAULT_CLEAR` — all fault bits returned to inactive
- `STALL_CLEAR` — all stall bits returned to inactive
This lets the client update UI state immediately without polling. The client
currently discovers fault clearance only via GET_STATUS polling.

**DISAGREE** on periodic reminders for active faults. Over-engineering. Snapshot-on-
enable + CLEAR events + edge triggers + existing GET_STATUS polling covers all cases.
A persistent fault is visible via GET_STATUS; we don't need a redundant reminder.

#### Q5 — Enable/disable

**DISAGREE** that two command names create "avoidable API ambiguity". The ENTIRE
existing command set has dual SCPI + legacy names — this is the established pattern
(e.g., `SYST:HB:SET` + `SET_HEARTBEAT`, `SYST:FAULT:CLR` + `CLEAR_FAULT`). Adding
`SYST:EVT:EN` + `EVENT_ENABLE` is consistent, not ambiguous. Removing legacy aliases
would be the inconsistency.

**DISAGREE** on default mask including critical events at boot. Events disabled at
boot means no unsolicited output until the client is ready to parse them. This
matters because:
- During connection handshake (SET_FORMAT, initial refresh), unsolicited events

- Critical faults are already visible via the initial GET_STATUS refresh.
- Snapshot-on-enable ensures no faults are missed after subscribe.

Sequence: connect → SET_FORMAT → refresh → EVENT_ENABLE → (snapshot sent) → normal operation.

**AGREE** on mask parameter: `SYST:EVT:EN <mask>` (0 = disable, 0x07 = all).
`SYST:EVT:EN` with no arg defaults to `EVT_MASK_ALL` for convenience.

### Revised Event Contract (v1)

**Event types:**
| Type | Category | Trigger |
|---|---|---|
| `FAULT` | Critical | Any fault bit asserts (OCD, UVLO, TH_SD) |
| `FAULT_CLEAR` | Critical | All fault bits return to inactive |
| `STALL` | Critical | STALL_A or STALL_B asserts |
| `STALL_CLEAR` | Critical | All stall bits return to inactive |
| `MOTION_DONE` | Informational | BUSY transitions from active to inactive |

**Required fields:**
| Field | Type | Description |
|---|---|---|
| `type` | string | Event type name (e.g. "FAULT") |
| `seq` | uint32 | Monotonic sequence number (per-boot) |
| `ts_ms` | uint32 | MCU tick at event detection (ms) |
| `data` | object | Event-specific payload |

**Data payload per event type:**
- `FAULT`: `{"status": <raw_status_reg>, "detail": "OCD|UVLO|TH_SD"}`
- `FAULT_CLEAR`: `{"status": <raw_status_reg>}`
- `STALL`: `{"status": <raw_status_reg>, "bridge": "A|B|AB"}`
- `STALL_CLEAR`: `{"status": <raw_status_reg>}`
- `MOTION_DONE`: `{"status": <raw_status_reg>}`

**Delivery guarantees:**
- Edge-triggered: events fire once per transition, not continuously
- Snapshot-on-enable: active critical conditions emitted on `SYST:EVT:EN`
- Queue overflow: drop newest, increment lost counter, never block producer
- Ordering: events delivered in detection order (FIFO queue)

**Wire format — JSON mode:**
```json
{"kind":"event","type":"FAULT","seq":1,"ts_ms":12345,"data":{"status":4660,"detail":"OCD"}}
```

**Wire format — ASCII mode:**
```
!FAULT status=0x1234 detail=OCD
```

**Commands:**
| SCPI | Legacy alias | Description |
|---|---|---|
| `SYST:EVT:EN [mask]` | `EVENT_ENABLE [mask]` | Enable events (default mask=0x1F=all) |
| `SYST:EVT:DIS` | `EVENT_DISABLE` | Disable all events |
| `SYST:EVT:STAT?` | `EVENT_STATUS` | Query: mask, sent count, lost count |
