# Architecture ground truth for diagramming

Written for an agent that must draw the StepperMotorController firmware architecture
(graph, chart, Mermaid, whatever) from how the code is **actually** built.
Everything below was measured from the source tree on 2026-10-05 (uncommitted working
tree on `master`). Where the code disagrees with the markdown docs, this file says so.

Do not use `CODE_PHILOSOPHY.md`, `README.md` or anything under `docs/archive/` as a
source of nodes or edges. They describe intent. Use this file plus the two generated
files it points at.

**Harness internals worth drawing separately** (they are not one homogeneous box):

- `harness/defs/` — the six boundary headers. Each is one struct of references plus a
  signal table plus one `connect*()` declaration. All `connect*()` bodies are in
  `harness/defs/harness_connect.cpp`.
- `harness/pins/` — 76 files. **36 of them are one-line forwarders** that just
  `#include` a layer's own `boundary/` header (example: `harness/pins/imotor_driver.hpp`
  contains only `#include "L4_drivers/boundary/imotor_driver.hpp"`). The other ~40 are
  real shared PODs and init contracts (`MotorCommand`, `AsyncEvent`, telemetry types,
  pin bundles, `clock_board.hpp`, `spi_init.hpp`, `*_task_init.hpp`, `IResponseSink`).
- `harness/taps/` — `TracedLock`, `TracedSPIBus`, `TracedMotorDriver`, `TracedTransport`,
  `TracedEncoder`, applied via `applyTap<Tap, Slot, Iface>()`. Compiled only with
  `ENABLE_INTERFACE_TRACE` (on in the `firmware-debug` preset, off in release).
- `harness/trace/interface_trace.{hpp,cpp}` — the `ITRACE(...)` macro and sink. Included
  **directly** by 7 L3 files and 2 L2 files (`command_parser.cpp`, `event_codec.cpp`).

## 3. Measured include edges (what the compiler sees)

Counted with a script over every `#include` in `server/` (vendor excluded), grouped by
sheet. Self-includes and C standard headers dropped. "pins" = `harness/pins/`.
"defs:X" = that specific harness header.

```
L1  -> defs:harness_l5_l1_bytes.hpp 1 | pins 6
L2  -> defs:harness_l1_l2.hpp 1 | defs:harness_l2_l3.hpp 2 | pins 12 | harness/trace 2
L3  -> defs:harness_l2_l3.hpp 3 | defs:harness_l3_l4.hpp 31 | defs:harness_tasks_l3.hpp 4 | pins 75 | harness/trace 7 | PLATFORM 22
L4  -> defs:harness_l4_l5.hpp 13 | pins 11 | PLATFORM 2
L5  -> defs:harness_l4_l5.hpp 5 | defs:harness_l5_l1_bytes.hpp 1 | pins 17 | PLATFORM 1 | CMSIS/FreeRTOS/SEGGER 16
TASKS    -> defs:harness_tasks_l3.hpp 4 | pins 6 | PLATFORM 14
PLATFORM -> pins 22 | CMSIS/FreeRTOS/SEGGER 22
SYSTEM   -> L3 8 | TASKS 3 | PLATFORM 1 | pins 5 | defs:harness_tasks_l3.hpp 1 | defs:harness_l5_l1_bytes.hpp 1 | harness/trace 1
defs     -> L1 2 | L2 1 | L3 17 | L4 7 | L5 7 | PLATFORM 3 | pins 13
pins     -> L1 2 | L2 1 | L3 20 | L4 5 | L5 4 | TASKS 4 | PLATFORM 9
```

Key reading: **no layer includes another layer's directory directly.** Every L↔L edge
goes through `harness/defs/` or `harness/pins/`. `check_includes.py --strict` reports 0
violations.

### 3a. Edges that cross layers through a pins forwarder

Because 36 pins files are forwarders, some cross-layer reach is hidden behind `pins/`.
Resolved to the layer the forwarder exposes:

| From | To | Via | Count | Note |
|---|---|---|---|---|
| L2 | L1 | `pins/itransport.hpp` | 2 | L2 sees `Transport::ITransport` through the forwarder as well as through `harness_l1_l2.hpp`. Same type, two include paths. |
| L5 | L1 | `pins/ibyte_channel.hpp` | 2 | the rule-3 exception (L5 implements L1's interface) |
| L3 | TASKS | `pins/{motor,comms,encoder,display}_task_init.hpp` | 4 | **L3 creates the RTOS tasks.** `initMotorSubsystem` etc. call `Harness::initMotorTask(...)`, whose definition lives in `F_platform/tasks/motor_task_init.cpp` (`namespace Harness`). |
| L3 | L3, L4 | L4, L5 | L5 | many | same-layer forwarders; not cross-layer |

Everything else resolved to the same layer that included it.

## 4. Composition and init order (from `server/main.cpp` + `system_init.cpp`)

```
main()
  System::initHardware()
    Services::initClockBoard()          -> Harness::initClockBoard()   [L5 init/clock_board.cpp]   (L3 shim: L3_services/infra/board_init/board_init.cpp)
    Services::initDebugOutput()         -> Harness::initDebugOutput()  [PLATFORM hw/early_debug_board.cpp, namespace Harness]
    Platform::initMicrosecondClockTIM5()           [PLATFORM hw/microsecond_timer_tim5.cpp]
    Services::TickTimer_Init(usClock)              [L3 infra/tick_timer]
    Harness::setMicrosecondClock(&usClock)         [pins/imicrosecond_clock.cpp, global accessor]
    Trace::initTraceSink()                         [L3 infra/trace -> Harness::ITrace::setSink]
  System::initPlatform()
    Harness::initPlatformBoard(s_platform)         [PLATFORM rtos/platform_init.cpp] creates 6 mutexes + 2 queues + clock/scheduler/stats/critical/notifier
    Harness::initSPIManager(TracedLock<0>(spi1Lock), TracedLock<1>(spi2Lock))   [L5 init/spi_init.cpp -> Board::g_spiManager]
  System::initServices()
    Platform::setTaskStatsProvider(r.taskStats)
    Services::initSystemServices(controlModeLock, eventQueue, telemetryLock, uiModeLock, clock)   [L3 motion/system_service_init.cpp]
  System::initTasks()
    Services::initMotorSubsystem(motorCmdQueue, clock, scheduler, commandQueueLock, taskStats, out)
        connectL3L4(clock)  --(first call)--> L4 init contracts --> connectL4L5() --> L5 init contracts
        g_motorService.init(...); Harness::initMotorTask(...) ; g_commandQueue.init(...)
    Services::initEncoderSubsystem(clock, scheduler, critical, usClock, out)   -> connectL3L4 (cached) ; Harness::initEncoderTask  (SKIP if no encoder hw)
    Services::initDisplaySubsystem(clock, scheduler, out)                       -> connectL3L4 (cached) ; Harness::initDisplayTask
    Services::initCommsSubsystem(deps, clock, scheduler, notifier)
        connectL3L4 (cached) ; initDispatches(...) -> L3Dispatchers
        Protocol::initCommsProtocol(out, dispatchers, clock)                     [L2]
            Transport::initTransport(out, VCP_UART, clock)                       [L1]
                Harness::connectL5L1Bytes(CommsChannel::VCP_UART) -> Board::initCommsBoard -> UartHardware
            connectL1L2(rawTransport)  (TracedTransport)
            ServiceDispatcher.bind(dispatchers); CommandParser(l1l2.transport, dispatcher)
        connectL2L3(dispatchers, parser)
        g_commsService.init(...) ; Harness::initCommsTask(...)
    Harness::setTaskHandles({motor, comms, display})      <-- encoder handle NOT published (see §8)
    Harness::setCommsRxWake(r.notifier, g_commsTaskHandle)  [L5 comms_board.cpp -> UartHardware::setRxWake]
  System::start()  -> vTaskStartScheduler()
```

So the *init* dependency direction is SYSTEM → L3 → (L2 → L1 → L5-bytes) and
L3 → L4 → L5 via the connect functions, plus L3 → TASKS for task creation.
The *runtime call* direction is TASKS → L3 → L4 → L5 and L2 ⇄ L3 for commands.

### Tasks (constants in `F_platform/tasks/*_task.hpp`)

| Task | Prio | Stack (words) | Loop (verbatim behaviour) | L3 entry called |
|---|---|---|---|---|
| Motor | 4 | 1024 | `delayMs(100)`; then `queue.receive(cmd, 50 ms)` → `onCommand(cmd)`; every ≥50 ms → `periodicUpdate()` | `Services::IMotorService` (`g_motorService`) |
| Comms | 3 | 2048 | `delayMs(200)`; `onStart()`; loop: `tick()`; then `rxWake->waitForNotification(10 ms)` if notifier set, else `sleepUntilMs(10)` | `Services::ICommsService` (`g_commsService`) |
| Encoder | 2 | 128 | `sleepUntilMs(10)` → `sample()`; task not created when encoder hardware absent | `Services::IEncoderService` (`g_encoderService`) |
| Display | 1 | 640 | `sleepUntilMs(50)` → `tick()` | `Services::IDisplayService` (`g_displayService`) |

What the entries do (so the chart can show secondary fan-out):

- `MotorService::onCommand` → `MotorController::processCommand`; `periodicUpdate` →
  `MotorController::periodicUpdate` + writes `SystemTelemetry` into `TelemetryStore`.
- `CommsService::tick` → `ICommandProcessor::process()` + `checkBaudRevert()`; emits
  telemetry every `TELEMETRY_PERIOD_MS` if enabled; drains `s_eventQueue` → `emitEvent`;
  heartbeat timeout check.
- `EncoderService::sample` → reads the L5 DMA ring through `IEncoderHardware`
  (`sampleBuffer/sampleWriteIndex`), feeds `EncoderProcessor`, computes window velocity.
- `DisplayService::tick` → `handleJoystick()`; if `UIMode::LOCAL` → `ScreenManager::render()`.

Task suspend/resume callers (via `Platform::IScheduler` + `Harness::taskHandles()`):
`MotorService::setStepModeSafe` (motor), `DebugService` (motor and display).

The immediate ESTOP path bypasses the motor queue: `CommandQueue` (Comms task) →
`IImmediateStop::immediateHardHiZ()` (`MotorService`) → `MotorController::emergencyHiZ()`
→ `IMotorDriver::hardHiZ()` on the powerSTEP01 over SPI1 (SPI lock taken by the driver). No flag is set; the Motor task learns of the stop only through driver status on its next `periodicUpdate`.

## 8. Where code and docs disagree (draw the code, not the doc)

1. **Taps are applied in two places, not one.** `harness_connect.cpp` applies
   `TracedSPIBus`, `TracedMotorDriver`, `TracedEncoder`, `TracedTransport`.
   `system_init.cpp::initPlatform` applies `TracedLock` slots 0/1 itself. CODE_PHILOSOPHY
   §14 claims connect.cpp is the only place.
2. **Encoder task handle is never published.** `TaskHandles` has an `encoder` field;
   `system_init.cpp` sets only motor/comms/display. `encoder_task_init.cpp` keeps its handle
   local. Nothing reads `taskHandles().encoder` today.
3. **L3 creates tasks.** Rule 1 says tasks call services; it is also true that L3's
   `init*Subsystem` functions call `Harness::init*Task()` (defined in `F_platform/tasks/`).
   So there is a TASKS→L3 runtime edge *and* an L3→TASKS init edge.
4. **L3 fronts two early board inits.** `Services::initClockBoard` /
   `Services::initDebugOutput` in `L3_services/infra/board_init/board_init.cpp` are one-line
   shims to `Harness::initClockBoard` (L5) and `Harness::initDebugOutput` (PLATFORM `hw/`).
   SYSTEM calls L3 for these; L3 does nothing with them. That is an L3→L5 reach through a
   pins init contract, not through H_L3_L4/H_L4_L5.
5. **A PLATFORM file defines `Harness::` functions.** `F_platform/hw/early_debug_board.cpp`
   is `namespace Harness`. Likewise all four `F_platform/tasks/*_task_init.cpp` define
   `Harness::init*Task`. The manifest groups them by directory (PLATFORM / TASKS), not by
   namespace.
6. **Two include paths to `ITransport` from L2**: `harness_l1_l2.hpp` and the forwarder
   `pins/itransport.hpp`. Same type; the checker allows both.
7. **`harness/pins/` is half forwarders.** 36 of 76 files only re-include a layer boundary
   header. A diagram that shows "pins" as a single node of shared types overstates it.
8. **Trace macros are included directly by L2 and L3**, not through a harness header
   (`harness/trace/interface_trace.hpp`: 7 L3 files, 2 L2 files, 1 SYSTEM).
9. **Global accessors exist beside the harness structs**: `Harness::microsecondClock()`
   (`pins/imicrosecond_clock.cpp`), `Harness::taskHandles()` (`defs/task_handles.cpp`),
   `Harness::getExtiCallback(line)` (`pins/exti_callbacks`), `Services::g_telemetryStore`.
   These are implicit edges from whoever calls them.
10. **Docs archived, not deleted**: `docs/archive/` still holds the Core/Inc-era
    documents. Their content is stale. Ignore for diagramming.

## 10. Suggested node/edge model for the drawing

- Nodes: L1, L2, L3, L4, L5, TASKS, PLATFORM, SYSTEM, and the harness split into
  `defs` (6 boundary headers), `pins` (PODs + init contracts; optionally a second
  "forwarders" sub-node), `taps`, `trace`.
- Solid edges: the 6 harnesses with their signal counts (1, 14, 7, 8, 1, 5), labelled by
  direction from the manifest.
- Dashed edges: the rule-3 exception L5→L1; the hidden edges from §3a and §8
  (L3→TASKS task creation, L3→L5 clock/debug init shims, L2/L3→trace, SYSTEM→L3).
- RTOS column: 4 tasks with prio/stack/period, 2 queues, 6 mutexes, 1 notification; ISR
  arrows from §6 into Comms (notify), Encoder (index callback + DMA ring), Display (TE flag).
- PLATFORM as a bus/power rail touching every node (22 includes from L3, 14 from TASKS,
  2 from L4, 1 from L5, 1 from SYSTEM, 0 from L1/L2).
