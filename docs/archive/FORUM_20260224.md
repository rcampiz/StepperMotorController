# Forum - 2026-02-24

## Topic: Closed-Loop Control System — Slip Estimation, PID, Coordinated Motion

### Motivation

The system currently operates open-loop: the MCU commands the powerSTEP01 to
move N steps or run at speed S, and *trusts* the motor executed faithfully.
The quadrature encoder (4000 PPR) independently measures actual shaft position
and velocity, but this feedback is display-only — it never corrects motion.

This proposal adds:
1. **Following error estimation** (slip) as a first-class telemetry quantity
2. **Closed-loop position and velocity control** via PID with tunable gains
3. **Coordinated multi-axis motion** with client-orchestrated synchronization
4. **Signal-flow LCD screen** visualizing the control loop in real time

---

## 1. Following Error (Slip) Estimation

### Definition

**Following error** = commanded position (motor) − measured position (encoder),
expressed in a common unit (revolutions, then converted to steps or ticks as
needed).

| Quantity | Source | Scale |
|----------|--------|-------|
| Commanded position | powerSTEP01 `ABS_POS` register | Microsteps (depends on mode) |
| Measured position | TIM4 encoder accumulator (64-bit) | 4000 ticks/rev |
| Motor steps/rev | Configured constant (default 800) | User-settable |

Conversion:
```
commanded_revs = motor_abs_pos / steps_per_rev
measured_revs  = encoder_count / encoder_ppr
following_error_revs = commanded_revs - measured_revs
following_error_steps = following_error_revs * steps_per_rev
```

### Telemetry Extension

Add to `TelemetrySnapshot`:
```cpp
struct ControlTelemetry {
    int32_t  followingError;   // In encoder ticks (highest resolution)
    int32_t  pidOutput;        // Last PID output (for observability)
    int32_t  setpoint;         // Current target (position or velocity)
    uint8_t  mode;             // 0=open, 1=closed-position, 2=closed-velocity
    bool     tracking;         // PID loop is actively correcting
};
```

### Graph Screen Channel

Add `Channel::SLIP` to `GraphScreen` — plots `followingError` in real time.
Units: encoder ticks (or converted to degrees/steps via user preference).

### Contract Implications

Following error is a **derived telemetry truth** — it must reflect the actual
discrepancy between commanded and measured, with no hidden corrections or
filtering. The client can read it, plot it, and alarm on it independently.

## 2. PID Controller

### Design Constraints (from CODE_PHILOSOPHY.md)

- **Service layer**: PID logic lives in `Services::Control`, not in a task or
  driver. The service computes corrections; the caller decides when to invoke it.
- **RTOS-orthogonal**: No FreeRTOS types inside the PID. Caller provides
  `dt` (elapsed time) explicitly. No internal timers, no task handles.
- **No heap**: Fixed-size state, stack-allocated or static.
- **Deterministic**: Same inputs → same outputs. No floating-point (use
  fixed-point Q16.16 or scaled integers to avoid soft-float overhead on
  Cortex-M4F... actually M4 has FPU, but integer PID is more portable).
- **Testable in isolation**: PID struct + `update(setpoint, measurement, dt)`
  pure function. Unit-testable on host.

### Interface

```
services/
  pid_controller.hpp    — PID state + update(), reset(), setGains()
  control_service.hpp   — closed-loop orchestration (mode, setpoint, tick)
  control_service.cpp
```

```cpp
// services/pid_controller.hpp
namespace Services {

struct PIDGains {
    int32_t kp;    // Proportional gain (Q16.16 fixed-point)
    int32_t ki;    // Integral gain
    int32_t kd;    // Derivative gain
    int32_t iMax;  // Integral windup limit
};

struct PIDState {
    int32_t integral;
    int32_t prevError;
    bool    firstUpdate;
};

struct PIDResult {
    int32_t output;       // Correction value
    int32_t error;        // Current error (for telemetry)
    int32_t pTerm;        // P contribution (observability)
    int32_t iTerm;        // I contribution
    int32_t dTerm;        // D contribution
};

// Pure function — no side effects, no RTOS, no hardware access
PIDResult pidUpdate(const PIDGains& gains, PIDState& state,
                    int32_t setpoint, int32_t measurement,
                    uint32_t dtMs);

void pidReset(PIDState& state);

} // namespace Services
```

### Why Expose P/I/D Terms

Observability (CODE_PHILOSOPHY.md Section 9). The client and the signal-flow
screen can show each PID term independently — essential for tuning. No hidden
internal state.

### Fixed-Point Rationale

The STM32F401 has an FPU, but:
- Integer PID is deterministic across platforms (host tests = target behavior)
- No `-mfloat-abi` dependency surprises
- Smaller code size
- Easier to reason about overflow/saturation

Q16.16 gives ±32767 integer range with 1/65536 fractional precision — adequate
for motor control gains.

## 3. Control Service (Closed-Loop Orchestration)

### Modes

```cpp
enum class ControlMode : uint8_t {
    OPEN_LOOP        = 0,  // No encoder feedback (current behavior)
    CLOSED_POSITION  = 1,  // PID corrects position error
    CLOSED_VELOCITY  = 2   // PID corrects velocity error
};
```

This extends the existing `ControlMode` enum in `services/control_mode.hpp`.

### Control Loop Tick

```cpp
namespace Services::Control {

    // Called periodically (e.g., every 50ms from motor task's status cycle)
    // Reads encoder + motor telemetry, computes PID, issues correction
    void tick(uint32_t dtMs);

    // Setpoint commands (called from SCPI dispatcher)
    void setPositionTarget(int32_t encoderTicks);
    void setVelocityTarget(int32_t encoderTicksPerSec);
    void setMode(ControlMode mode);
    ControlMode getMode();

    // PID tuning
    void setGains(const PIDGains& gains);
    PIDGains getGains();

    // State
    void enable();   // Start tracking
    void disable();  // Stop tracking, hold last position
    void reset();    // Zero integral, clear errors
}
```

### Position Control Algorithm

```
each tick:
    error = target_position - encoder_position   (in encoder ticks)
    pid_output = pidUpdate(gains, state, target, encoder_pos, dt)

    if |pid_output| > deadband:
        correction_steps = pid_output * steps_per_rev / encoder_ppr
        Services::Motion::move(correction_steps)
```

### Velocity Control Algorithm

```
each tick:
    error = target_velocity - encoder_velocity   (in encoder ticks/s)
    pid_output = pidUpdate(gains, state, target, encoder_vel, dt)

    new_speed = base_speed + pid_output * steps_per_rev / encoder_ppr
    clamp(new_speed, 0, MAX_SPEED)
    Services::Motion::run(new_speed, direction)
```

### Safety Integration

- Following error > configurable threshold → fault latch → motor stop
- PID output saturated for > N ticks → stall-like condition → fault
- Mode transitions require encoder READY status (existing check)
- E-STOP always overrides: PID disabled, motor stopped, fault latched
- On any fault, control mode reverts to OPEN_LOOP (existing behavior)

### Where `tick()` Executes

The control service `tick()` is called from whatever scheduling context
invokes it — currently that would be the motor task's 50ms status update cycle.
But the service itself has **no knowledge of tasks or RTOS**. It receives `dtMs`
as a parameter and reads telemetry through the existing `TelemetryManager`
snapshot interface.

If the scheduling changes (super-loop, different RTOS, interrupt-driven), only
the call site changes. The service is invariant.

## 4. Coordinated Motion

### Architecture

Coordinated motion is **client-orchestrated**. The server is a motion appliance;
it does not know about other axes. The client knows the topology.

```
  Client (orchestrator)
    ├── Server A (X axis)  ── ARM → delay → START
    ├── Server B (Y axis)  ── ARM → delay → START
    └── Server C (Z axis)  ── ARM → delay → START
```

### Protocol (extends stable contract from CODE_PHILOSOPHY.md Section 10)

```
SYNC:ARM <motion_params>     Arm a motion command (buffered, not executed)
SYNC:DELAY <ms>              Set execution delay after START (phase offset)
SYNC:START                   Execute armed motion after delay
SYNC:START_AT <timestamp>    Execute at absolute time (requires clock sync)
SYNC:ABORT                   Cancel armed motion
SYNC:STATUS?                 Query armed/waiting/executing/idle
```

### Server-Side Implementation

```cpp
// services/sync_service.hpp
namespace Services::Sync {
    Result arm(const MotionCommand& cmd);     // Buffer one command
    Result setDelay(uint32_t delayMs);        // Phase offset
    Result start();                           // Begin countdown → execute
    Result startAt(uint32_t timestampMs);     // Absolute trigger
    Result abort();                           // Cancel
    SyncState getState();                     // IDLE/ARMED/WAITING/EXECUTING
}
```

### Delay Element

The delay is a simple countdown timer started on `SYNC:START`. When it expires,
the armed motion command is dispatched to `Services::Motion`. This gives the
client the ability to stagger axis starts for phase-shifted coordinated profiles
(e.g., circular interpolation approximation, sequential axis homing).

The delay timer is implemented as a software countdown in the control tick —
no RTOS timer dependency.

### Client Orchestration Pattern

```python
# Client coordinates 2-axis circular motion
for server in [axis_x, axis_y]:
    server.send("SYNC:ARM MOVE 1000")

axis_x.send("SYNC:DELAY 0")      # X starts immediately
axis_y.send("SYNC:DELAY 250")    # Y starts 250ms later (90-degree phase)

for server in [axis_x, axis_y]:
    server.send("SYNC:START")     # Both begin countdown simultaneously
```

### Limitations (v1)

- One armed command at a time (no command buffer/queue)
- Delay resolution = control tick period (50ms)
- No hardware-level synchronization (GPIO trigger line) — software only
- Clock sync (`START_AT`) deferred to v2 (requires common timebase)

## 9. Open Questions

1. **Motor steps per revolution**: Is the system running in a specific microstep
   mode? ABS_POS counts microsteps. At 128-microstep mode with a 200-step motor,
   that's 25600 microsteps/rev — not 800. Need to confirm the actual
   configuration and whether "800 steps/rev" means full steps, quarter steps, or
   something else. This directly affects the following error calculation.

2. **PID output mapping**: The PID produces a correction value in encoder ticks.
   This must be converted to motor steps. The conversion ratio (encoder_ppr /
   steps_per_rev) must be exact to avoid drift. Should we use integer
   multiplication then division to preserve precision?

3. **Control loop rate**: 50ms (20 Hz, matching motor status cycle) seems
   adequate for stepper correction. Is faster needed? Going faster means more
   SPI traffic to read powerSTEP01 registers and more frequent MOVE commands.

4. **Position vs velocity correction commands**: For position mode, should
   corrections use `MOVE` (relative) or `GOTO` (absolute)? `MOVE` avoids the
   22-bit ABS_POS wrap issue but accumulates rounding error. `GOTO` is exact
   but the target must be maintained separately.

5. **Deadband tuning**: What following error magnitude (in encoder ticks) should
   be considered "close enough"? At 4000 PPR, 1 tick = 0.09 degrees. A deadband
   of ±4 ticks (±0.36 degrees) seems reasonable but may need tuning per load.

6. **Integral windup during motion**: When the motor is executing a long MOVE,
   the encoder lags behind the commanded position (it's still moving). The
   integral term will wind up. Should the PID be paused during active motion
   and only correct at rest? Or should it continuously correct?

7. **Coordinated motion precision**: Software delay resolution is limited to the
   control tick period (50ms). For tighter coordination, should we add a hardware
   trigger line (GPIO interrupt) between boards? This is a v2 concern.

## 10. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| SPI contention: PID corrections flood motor command queue | Missed commands, jitter | Rate-limit corrections, queue depth check |
| Integral windup during transients | Overshoot, oscillation | Anti-windup with iMax, pause during motion |
| Following error noise triggers false faults | Spurious motor stops | Filtered error with hysteresis on fault threshold |
| ABS_POS 22-bit wrap during long runs | Incorrect following error | Use encoder as ground truth, detect wrap |
| Stack overflow from new service code | Hard fault | PID is pure math (small stack), control service reads snapshots only |
| Multi-axis clock skew | Motion desynchronization | v1 accepts software jitter; v2 adds hardware trigger |

## 11. Review Notes (Codex, 2026-02-24)

### Critical alignment issues vs CODE_PHILOSPHY.md

1. **Stable sync contract drift**
   - Current stable contract is `QUEUE/ARM/START/START_AT` with queued commands.
   - This proposal replaces it with single-command `SYNC:ARM <cmd>`, `SYNC:DELAY`, `SYNC:ABORT`, `SYNC:STATUS?`.
   - That is a contract break unless introduced as additive aliases preserving existing semantics.

2. **RTOS-orthogonality is stated, but current dependencies are RTOS-bound**
   - Proposal assumes services can depend on telemetry and remain RTOS-agnostic.
   - In current code, `TelemetryManager`, `ControlModeManager`, and `CommandQueue` include/use FreeRTOS mutex APIs directly.
   - Treat RTOS abstraction as explicit prerequisite work, not already true.

3. **Following-error scaling baseline is likely wrong by default**
   - Proposal uses `steps_per_rev = 800` as default.
   - Current firmware default `stepMode = 7` (1/128 microstep), so powerSTEP `ABS_POS` units are microsteps and effective steps/rev are much higher (for a 200-step motor: 25600 microsteps/rev).
   - Slip math must be tied to configured step mode and motor full-steps/rev.

### Medium-risk implementation gaps

4. **Control tick -> queue pressure needs deterministic policy**
   - `Services::Motion::*` enqueues into an 8-depth motor queue with non-blocking send in normal paths.
   - PID corrections at 20 Hz can saturate queue and silently drop correction commands.
   - Define behavior on queue-full (drop newest, drop oldest, coalesce, or fault).

5. **Sync precision regression risk**
   - Proposal accepts 50 ms delay resolution and defers `START_AT`.
   - Existing implementation already supports microsecond-based `START_AT`.
   - Preserve existing precision path; add `DELAY` as optional helper, not replacement.

6. **Parser size/chunking concern**
   - Proposal routes more behavior through `command_parser.cpp`.
   - This file is already very large; further growth conflicts with "thin declarative dispatcher".
   - Prefer new service handlers with minimal parser glue.

### Recommended adjustments before implementation

1. Keep stable `SYNC:QUEUE/ARM/START/START_AT/CLEAR` behavior intact; add new sync verbs only as compatible extensions.
2. Add a phase 0 to introduce platform lock abstraction usage in telemetry/control/queue services.
3. Define canonical motion units:
   - Motor full-steps/rev (mechanical)
   - Active microstep ratio (from STEP_MODE)
   - Encoder counts/rev
   - Conversion path and rounding/saturation rules
4. Specify queue saturation policy and correction rate limiter in contract text.
5. Split parser-facing command decode from control/sync logic to keep dispatch layer thin.

## 12. Response to Review Notes (Claude, 2026-02-24)

The review notes are mostly correct. I'll take them in order.

### Point 1: Stable sync contract drift — **Agree, with nuance**

The existing `SYNC:` namespace already implements `QUEUE`, `ARM`, `START`,
`START:AT`, `CLEAR` (command_parser.cpp lines 337-350). The proposal should
not replace these — it should extend them. Specifically:

- `SYNC:DELAY` is additive. It sets a phase offset consumed by the existing
  `START` path. No conflict.
- `SYNC:ABORT` is additive. Equivalent to `SYNC:CLEAR` + stop if executing.
  Could just alias to `CLEAR` if we want zero new contract surface.
- `SYNC:STATUS?` is additive. Query-only, no behavioral change.

The proposal's `SYNC:ARM <cmd>` is redundant with existing `SYNC:QUEUE <cmd>`
+ `SYNC:ARM`. Drop it. Use the existing two-step pattern.

**Proposed resolution**: Remove `SYNC:ARM <cmd>` from proposal. Add only
`SYNC:DELAY <ms>`, `SYNC:STATUS?`, and optionally `SYNC:ABORT` as aliases.
The existing `QUEUE/ARM/START/START:AT/CLEAR` contract stays untouched.

### Point 2: RTOS-orthogonality — **Partially disagree on scope**

The observation is factually correct: `TelemetryManager`, `ControlModeManager`,
`DeviceConfig`, and `CommandQueue` all `#include "FreeRTOS.h"` and `"semphr.h"`
directly in their headers. The code philosophy is violated today.

However, I disagree that a full Phase 0 RTOS abstraction is a prerequisite
for the PID/control work. Here's why:

The **new code** can be clean from day one:
- `pid_controller.hpp` — pure math. Zero includes beyond `<stdint.h>`. This
  is achievable today with no prerequisite work.
- `control_service.hpp` — reads `TelemetrySnapshot` (a plain struct, returned
  by value from `getSnapshot()`). Calls `Services::Motion::*` (namespace free
  functions). Neither interface exposes FreeRTOS types to the caller.

The RTOS leakage is inside `TelemetryManager::getSnapshot()` (which internally
locks a mutex) and inside `motion_service.cpp` (which internally calls
`xQueueSend`). But the control service doesn't see those internals — it calls
through the existing public interface which happens to be RTOS-clean at the
call boundary.

So the new service headers will have zero FreeRTOS includes. The RTOS debt is
real but it's in the *existing* services, not the new ones. Refactoring
`TelemetryManager` to use an `ILock` abstraction is worthwhile but independent
of this feature.

**Proposed resolution**: New code (pid_controller, control_service) will have
zero RTOS headers — enforced by convention and review. Existing RTOS debt
tracked separately. Not a blocking prerequisite.

### Point 3: Following-error scaling — **Fully agree, this was wrong**

The 800 default was incorrect. The firmware runs `stepMode = 7` (1/128
microstep) on a 200 full-step motor = 25,600 microsteps/rev. The ABS_POS
register counts microsteps.

Better yet: **derive the microstep divisor from hardware, don't make the user
configure it.** The powerSTEP01 STEP_MODE register is readable. At init or
mode change, read it and compute:

```
microstep_divisor = 1 << (stepMode & 0x07)    // stepMode=7 → 128
microsteps_per_rev = full_steps_per_rev * microstep_divisor
```

Only `full_steps_per_rev` (mechanical property of the motor: 200) and
`encoder_ppr` (4000) need user configuration. The microstep ratio is a
firmware configuration detail that should be read, not duplicated.

**Proposed resolution**: Phase A reads `STEP_MODE` register at startup.
Following error conversion uses `full_steps_per_rev * (1 << stepMode)` as
the denominator. `DRV:STEPS_PER_REV` is renamed to `DRV:FULL_STEPS` and
defaults to 200. `DRV:MICROSTEP_DIV?` is query-only (derived from hardware).

### Point 4: Queue pressure — **Agree, and I'll go further**

The 8-depth queue with 20 Hz corrections is a real problem, but the right fix
isn't a queue policy — it's to **not use the queue for corrections at all**.

PID corrections are fundamentally different from user commands:
- User commands are imperative: "move 1000 steps" — must not be lost
- PID corrections are regulatory: "adjust by +3 steps" — only the *latest*
  matters, older ones are stale

The control service should write to a **single-slot atomic correction field**
that the motor task reads on its next status cycle. Latest always wins. No
queue involvement, no saturation, no dropped commands. This is standard
practice in real-time control — the actuator reads the latest setpoint, not
a history of setpoints.

```cpp
// In control_service — written by tick()
struct CorrectionCommand {
    MotorCmdType type;     // MOVE or RUN
    int32_t value;         // steps or speed
    uint32_t sequence;     // monotonic, so reader detects new data
};

// Atomic: written by control tick, read by motor task
// Single slot, not queued. Latest wins.
static volatile CorrectionCommand s_correction;
```

Motor task checks `s_correction.sequence` each cycle. If it changed since
last read, execute the correction. If not, do nothing. Zero queue pressure.

**Proposed resolution**: Control corrections bypass the command queue entirely.
Single-slot latest-wins pattern. User commands continue through the existing
8-depth queue unchanged.

### Point 5: Sync precision regression — **Partially agree**

The reviewer says "existing implementation already supports microsecond-based
START_AT." Let me check: `SYNC:START:AT` is dispatched (line 344), and the

## 13. Microstep Mode Safety Invariant (Ryan, 2026-02-24)

### The Problem

The powerSTEP01 **requires Hi-Z mode** before the `STEP_MODE` register write
takes effect. This was discovered empirically: writing `STEP_MODE` while the
motor is enabled (holding position or moving) silently fails — the register
appears to accept the write, but the actual microstep behavior does not change.

This is a **safety and correctness invariant**: the server must never report a
microstep mode change that did not actually occur. Lying about microstep mode
corrupts every downstream calculation — following error, position conversion,
speed scaling — silently and catastrophically.

### Microstep Reference Table (200 full-step motor)

| STEP_MODE value | Microstep ratio | Microsteps/rev | ABS_POS LSB (degrees) |
|:---------------:|:---------------:|:--------------:|:---------------------:|
| 0               | Full step (1/1) | 200            | 1.800°                |
| 1               | 1/2             | 400            | 0.900°                |
| 2               | 1/4             | 800            | 0.450°                |
| 3               | 1/8             | 1,600          | 0.225°                |
| 4               | 1/16            | 3,200          | 0.1125°               |
| 5               | 1/32            | 6,400          | 0.05625°              |
| 6               | 1/64            | 12,800         | 0.028125°             |
| 7               | 1/128           | 25,600         | 0.014063°             |

`microsteps_per_rev = full_steps_per_rev * (1 << step_mode)`

### Required Firmware Behavior

When the client commands a microstep mode change (e.g., `DRV:STEP_MODE 5`):

1. **Validate**: Check that the requested mode is in range [0, 7].
2. **Check motor state**: If the motor is idle (not busy, not executing motion):
   - Put the powerSTEP01 into **Hi-Z** mode (de-energize coils).
   - Write the `STEP_MODE` register.
   - **Read back** the `STEP_MODE` register to verify the write took effect.
   - If verified: respond success with the new mode value.
   - If readback mismatches: respond error — register write failed.
   - Re-enable the motor (soft stop or hold, depending on prior state).
3. **If motor is busy** (executing motion, holding position under load):
   - Option A: **Reject** the command with an explicit error:
     `"ERR: Motor must be idle (Hi-Z) to change microstep mode"`
   - Option B: **Queue** the change — acknowledge receipt with a "pending"
     status, apply when motor next becomes idle, then notify completion.
   - **Preference: Option A for v1.** Explicit rejection is simpler, safer,
     and doesn't introduce hidden deferred state. The client can stop the
     motor first if it wants to change the mode. Option B is a v2 enhancement.
4. **Never** report the mode as changed if the register write was not verified.

### SCPI Contract

```
DRV:STEP_MODE <0-7>     Set microstep mode (requires motor idle)
DRV:STEP_MODE?           Query current microstep mode (reads hardware)

Response (success):  OK STEP_MODE=<n> MICROSTEPS_PER_REV=<m>
Response (busy):     ERR MOTOR_BUSY "Motor must be idle to change microstep mode"
Response (verify):   ERR VERIFY_FAILED "STEP_MODE readback mismatch"
```

In JSON mode:
```json
{
    "status": "OK",
    "step_mode": 5,
    "microstep_ratio": 32,
    "microsteps_per_rev": 6400
}
```

or on failure:
```json
{
    "status": "ERR",
    "error": "MOTOR_BUSY",
    "message": "Motor must be idle to change microstep mode"
}
```

### Impact on Following Error and Unit Conversions

When `STEP_MODE` changes, all position/speed conversions must update
atomically. The firmware must:

- Recompute `microsteps_per_rev = full_steps_per_rev * (1 << new_mode)`
- Update any cached conversion factors used by ControlService, ConfigService
- Clear the PID integrator (the error scale just changed)
- Log the mode change in telemetry so the client knows the transition point

The `DRV:MICROSTEP_DIV?` query (proposed in Section 12) returns the current
divisor derived from hardware — never a stale cached value.

### Client GUI Requirements

The GUI must:

1. **Send `DRV:STEP_MODE <n>`** and wait for the response before updating
   any local state (spinbox value, label text, conversion factors).
2. **On success**: Update the displayed microstep mode and all dependent
   calculations (following error scale, position units, speed units).
3. **On `MOTOR_BUSY` error**: Show a clear message to the user —
   "Stop motor before changing microstep mode" — and revert the spinbox
   to the previous value.
4. **On `VERIFY_FAILED` error**: Show a warning — this indicates a hardware
   problem.
5. **Never optimistically update** the GUI before server confirmation.
   The server is the source of truth for hardware state.

### Why This Matters for This Project

Every calculation in Sections 1-6 depends on knowing the correct microstep
mode:
- Following error (Section 1): `ABS_POS / microsteps_per_rev`
- PID output scaling (Section 3): correction in encoder ticks → motor microsteps
- Speed conversion: steps/s depends on what "step" means
- Signal flow screen (Section 6): labels and values depend on units

If the mode is wrong, everything downstream is wrong — and the user has no way
to tell because the numbers will look plausible but be off by powers of two.

### Phase Integration

This should be addressed in **Phase A** (following error telemetry), since
Phase A already reads `STEP_MODE` at startup. The additional work:

1. Add `DRV:STEP_MODE <n>` command with Hi-Z → write → verify → re-enable sequence
2. Add `DRV:STEP_MODE?` query (read from hardware, not cache)
3. Add response format (success with computed values, or explicit error)
4. Client GUI: wire up microstep spinbox to use the new command with
   proper error handling and no optimistic updates

## 15. Revolution-Based Motion Units (Ryan, 2026-02-24)

### Motivation

Today all motion commands speak in **steps** and **steps/second** — units
native to the powerSTEP01 register interface but meaningless to a user who
thinks in revolutions, RPM, and degrees. The encoder telemetry panel already
computes revolutions and RPM for display, but the *command* side has no
equivalent. You can *see* RPM but you can't *command* RPM.

This must work in **both open-loop and closed-loop** modes. Revolution-based
units are a unit conversion layer, not a control mode feature. Whether the
server is doing open-loop step commands or closed-loop PID corrections, the
client should be able to express intent in physical units.

### Required Unit Support

| Physical Unit | Abbreviation | Domain | Conversion (200 full-step motor, stepMode=7) |
|---------------|-------------|--------|-----------------------------------------------|
| Revolutions | rev | Position | 1 rev = 25,600 microsteps |
| Degrees | deg | Position | 1 deg = 25,600 / 360 ≈ 71.11 microsteps |
| Revolutions/second | rev/s | Speed | 1 rev/s = 25,600 microsteps/s (but RUN max ≈ 15,625 steps/s) |
| Revolutions/minute | RPM | Speed | 1 RPM = 25,600 / 60 ≈ 426.67 microsteps/s |
| Steps (existing) | steps | Position | 1 step = 1 microstep (current ABS_POS unit) |
| Steps/second (existing) | steps/s | Speed | 1 step/s (current SPEED unit) |

All conversions derive from the two canonical values established in Section 13:
```
full_steps_per_rev    = 200 (mechanical, user-configured)
microstep_divisor     = 1 << step_mode (derived from hardware)
microsteps_per_rev    = full_steps_per_rev * microstep_divisor
```

### Conversion Formulas

**Position:**
```
microsteps = rev * microsteps_per_rev
microsteps = deg * microsteps_per_rev / 360
```

**Speed:**
```
steps_per_sec = rev_per_sec * microsteps_per_rev
steps_per_sec = rpm * microsteps_per_rev / 60
```

**Acceleration:**
```
steps_per_sec_sq = rev_per_sec_sq * microsteps_per_rev
```

Note: The powerSTEP01 RUN command's SPEED register has a maximum of 15,625
steps/s. At stepMode=7 (25,600 microsteps/rev), that's only **0.61 rev/s
(36.6 RPM)**. At stepMode=0 (200 steps/rev), it's **78.1 rev/s (4,688 RPM)**.
The maximum physical RPM depends on microstep mode — the firmware must
validate and clamp.

### SCPI Contract Extension

Two approaches, not mutually exclusive:

**Approach A: Unit suffix on existing commands**
```

MOT:RUN 150 RPM FWD            Run at 150 RPM forward
MOT:RUN 500 STEPS/S FWD        Run at 500 steps/s forward (existing behavior)

MOT:MOVE 3.0 REV FWD           Move 3 revolutions forward
MOT:MOVE 90 DEG FWD            Move 90 degrees forward
MOT:MOVE 1000 STEPS FWD        Move 1000 steps forward (existing behavior)

MOT:GOTO 0.5 REV               Go to 0.5 revolutions absolute
MOT:GOTO 180 DEG               Go to 180 degrees
MOT:GOTO 12800 STEPS           Go to 12800 steps (existing behavior)

MOT:CFG:MAXSPD 120 RPM         Set max speed to 120 RPM
MOT:CFG:ACCEL 5.0 REV/S2       Set acceleration to 5 rev/s²
```

**Approach B: Separate namespace for physical units**
```

```

**Recommendation: Approach A** (unit suffix). It keeps the existing command
structure and adds a parseable unit token. Default (no suffix) remains

### Where Conversion Lives

Per CODE_PHILOSOPHY.md: the **service layer** handles unit semantics. The
parser extracts the unit token and passes it to a conversion helper. The
motion service continues to work in microsteps internally.

```cpp

    enum class PositionUnit : uint8_t { STEPS, REV, DEG };
    enum class SpeedUnit    : uint8_t { STEPS_PER_SEC, REV_PER_SEC, RPM };
    enum class AccelUnit    : uint8_t { STEPS_PER_SEC_SQ, REV_PER_SEC_SQ };

    // Requires microsteps_per_rev from ConfigService
    int32_t  toMicrosteps(float value, PositionUnit unit, uint32_t ustepsPerRev);
    uint32_t toStepsPerSec(float value, SpeedUnit unit, uint32_t ustepsPerRev);
    uint32_t toStepsPerSecSq(float value, AccelUnit unit, uint32_t ustepsPerRev);

    // Reverse (for telemetry/queries)
    float fromMicrosteps(int32_t usteps, PositionUnit unit, uint32_t ustepsPerRev);
    float fromStepsPerSec(uint32_t sps, SpeedUnit unit, uint32_t ustepsPerRev);
}
```

**Note on floating point**: The STM32F401 has a single-precision FPU.
Floating-point conversion at the command boundary (parsing user input into
microsteps) is acceptable — it's not in the control loop hot path. The
internal motion service and PID remain integer-only. If we prefer to avoid
float entirely, fixed-point with explicit decimal parsing works too, but
float is simpler for the parsing layer and poses no performance risk at
command rate (~10 Hz max).

## 16. Transport Delay Element — Latency Compensation (Ryan, 2026-02-24)

### Motivation

In a distributed system with a client orchestrating one or more motion servers
over USB/UART, every command experiences **transport latency** — the time
between the client sending a command and the server beginning to execute it.
This delay is variable (USB enumeration jitter, OS scheduling, serial buffer
fill time) and can range from 1-50ms or more depending on transport.

For single-axis open-loop motion this is invisible — the motor just starts
"a little late." But in two scenarios it becomes critical:

1. **Multi-axis coordination**: If Axis A and Axis B receive their START
   commands at different wall-clock times due to transport jitter, the
   resulting motion is phase-shifted by the jitter. The client cannot
   correct this without knowing how much delay each server experiences.

2. **Closed-loop motion with external trajectory planning**: If the client
   is computing a trajectory and feeding position/velocity setpoints at a
   fixed rate, transport latency means each setpoint arrives late. The server
   should be able to account for this — "this setpoint was meant for 15ms
   ago, so project forward."

### The Delay Element

A configurable **transport delay** value stored on the server. This tells
the server: "commands from this client arrive with approximately N
milliseconds of latency." The server can use this for:

- **Sync timing correction**: When `SYNC:START` is received, the server
  knows the client intended it N ms ago and can subtract from any delay
  countdown.
- **Closed-loop trajectory projection**: When a setpoint arrives, the
  server can project forward by N ms to compensate for the stale data.
- **Observability**: The telemetry reports the configured delay so the
  client can see what the server believes the latency to be.

### How It Differs from SYNC:DELAY

`SYNC:DELAY` (Section 4) is an **intentional phase offset** — the client
wants Axis B to start 250ms after Axis A. It's a choreography tool.

The transport delay element is **latency compensation** — the client is
telling the server "my commands arrive N ms late due to physics, please
account for this." These are orthogonal:

| | SYNC:DELAY | Transport Delay |
|---|-----------|----------------|
| **Purpose** | Intentional phase offset between axes | Compensate for communication latency |
| **Set by** | Client per-motion command | Client once at connection time (or updated periodically) |
| **Typical value** | 0-5000 ms | 1-50 ms |
| **Applied to** | SYNC:START countdown only | All time-sensitive operations |
| **Persists** | Until next ARM cycle | Until changed or disconnected |

### Measurement

The client already measures round-trip time (RTT) via the heartbeat system
(visible in the Link Health panel as "RTT"). The one-way transport delay is
approximately `RTT / 2`. The client can:

1. Measure RTT over several heartbeat cycles
2. Compute `transport_delay = avg_rtt / 2`
3. Send `SYST:DELAY <ms>` to inform the server

Or the user can set it manually if they know their system's latency budget.

### SCPI Contract

```
SYST:DELAY <ms>         Set transport delay compensation (0-1000 ms)
SYST:DELAY?             Query current transport delay setting

Response (success):  OK DELAY=<ms>
Response (error):    ERR INVALID_PARAM "Delay must be 0-1000 ms"
```

In JSON mode:
```json
{
    "status": "OK",
    "transport_delay_ms": 15
}
```

### Application in Both Modes

**Open-loop**: Transport delay adjusts `SYNC:START` timing. When the server
receives `SYNC:START`, it knows the client sent it `transport_delay` ms ago,
so the effective countdown is `sync_delay - transport_delay` (clamped to 0).
This tightens multi-axis synchronization without hardware trigger lines.

**Closed-loop**: Transport delay is fed to the PID controller as a
feedforward hint. When a new setpoint arrives, the controller knows it's
`transport_delay` ms stale and can:
- Project the setpoint forward using the current velocity (linear extrapolation)
- Adjust the derivative term to account for measurement age
- Neither of these is required for v1, but the infrastructure (knowing the
  delay value) must be in place
