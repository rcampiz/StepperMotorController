Every command from the GUI — RUN, STOP, MOVE, GOTO, all of them — calls

blocks the entire event loop until a response arrives or a 2-second timeout

```
      → VcpTransport.send_line()     ← serial write
      → VcpTransport.recv_line()     ← serial read, 50ms timeout per attempt
    ← returns Response
  ← UI updates
```

There is no background thread in the active command path. The `SerialWorker`

> `# TODO: Move serial I/O to background thread`

So yes, the GUI thread blocks. The infrastructure to fix it exists but nobody
connected the wires. This is the single largest contributor to perceived
sluggishness.

### 2. The firmware adds 0–10ms of completely unnecessary idle time

`comms_task.cpp:137`:
```cpp
vTaskDelayUntil(&lastWakeTime, pdMS_TO_TICKS(COMMS_POLL_PERIOD_MS));  // 10ms
```

The CommsTask sleeps for a fixed 10ms between polls of the UART ring buffer.
Bytes arrive via interrupt into `RingBuffer<256>`, then sit there doing
absolutely nothing until the task wakes up. Average added latency: 5ms. Worst
case: 10ms.

The MotorTask, by contrast, blocks on `xQueueReceive` and wakes *immediately*
when a command is posted. The CommsTask should do the same — use a task
notification from the UART ISR to wake the task when a complete line arrives
(i.e., when `\n` is received). This is RTOS 101.

### 3. Character echo adds blocking TX during the parse loop

`command_parser.cpp:96-98`:
```cpp
char echo[2] = {static_cast<char>(byte), '\0'};
m_transport.print(echo);
```

Every printable byte received triggers a **polling/blocking** UART TX
(`uart_transport.cpp:174: while ((usart->SR & USART_SR_TXE) == 0) {}`). At
115200 baud, each character costs ~87µs of busy-wait. A 10-char command like
`RUN 1000 1` echoes 10 bytes = ~870µs of TX blocking interleaved with RX
processing. This isn't catastrophic, but it's needless work in a machine-to-
machine protocol where nobody is watching a terminal.

### 4. No telemetry means no feedback — the system *feels* broken

Telemetry is disabled on both ends:
- Firmware: `s_telemetryEnabled` defaults to `false`
- Client: telemetry timer is commented out

So after the user clicks "Run CCW" and gets "OK" back, the GUI shows... nothing.
No position updates, no speed readout, no visual indication the motor is
actually doing anything. The user has to manually click "Refresh" or issue
GET_STATUS to see state changes. This creates a perception of latency even when
the motor responded in under 20ms.

### 5. SPI bit-bang critical sections: a ticking time bomb (not yet detonated)

`spi_bitbang.hpp:198`: each SPI byte transfer wraps the entire 8-bit loop in
`taskENTER_CRITICAL()`, masking all interrupts for ~16µs at 1 MHz clock. The
motor task's periodic status update (STATUS + ABS_POS + SPEED = ~9 SPI bytes)
creates ~144µs of interrupt blackout every 50ms. At 115200 baud one UART byte
arrives every ~87µs, so in theory a byte could be missed during a status read.
In practice the UART peripheral has a 1-byte hardware buffer that prevents loss
during a single ~16µs blackout, so this isn't causing data loss *yet*.

However, when LCD rendering is re-enabled (currently `#if 0` in
`display_task.cpp:134`), SPI1 will be shared between motor and LCD via the
`SPIBitBang` mutex. LCD screen fills involve thousands of SPI bytes with
extended critical sections. That *will* cause UART byte loss. Something to
look forward to.

## Root cause: empty-line probe produces zero response from firmware

The connection probe in `main_window.py` sent `send_line("")` which transmits
`\r\n`. Looking at `command_parser.cpp` lines 77-88:

```cpp
// Handle newline (command complete)
if (byte == '\r' || byte == '\n') {
    if (m_bufIndex > 0) {   // ← ONLY echoes/dispatches if buffer has chars!
        m_transport.println("");
        m_buffer[m_bufIndex] = '\0';
        ParsedCommand cmd = parse(m_buffer);
        if (cmd.valid) { dispatch(cmd); }
        m_bufIndex = 0;
    }
    continue;   // ← Empty line (m_bufIndex == 0): NO echo, NO response, NOTHING
}
```

When `\r` arrives with an empty buffer (`m_bufIndex == 0`), the firmware skips
the entire echo/dispatch block and just `continue`s. Same for `\n`. **Zero bytes
are sent back to the host.** The `recv_line(timeout_ms=1000)` call in the probe
naturally times out and returns `None`, triggering "Firmware not responding".

This is NOT a pyserial issue, NOT a DTR issue, NOT a driver issue. It's the
firmware correctly (by design) ignoring empty commands, and the client probe
relying on a response that never comes.

## Fix applied

Changed `main_window.py` probe from empty line to `PING 0`:

```python
if not banner_ok:
    log.warning("No banner received — probing with PING...")
    self._transport.flush_input()
    self._transport.send_line("PING 0")
    probe = self._transport.recv_line(timeout_ms=2000)
    if probe is not None:
        log.info("Probe response: %r", probe)
        if probe.startswith("PING"):
            pong = self._transport.recv_line(timeout_ms=1000)
            if pong:
                log.info("Probe PONG: %r", pong)
    else:
        raise Exception("Firmware not responding...")
```

PING is guaranteed to produce a response (echo + PONG), as proven by both the
terminal emulator test and the diagnostic script.

## Reframing: this is a real-time motion service, not a hobby project

The user's architectural document redefines the context this entire thread has
been operating under. This is not a standalone stepper motor toy. It's:

- **STM32** = real-time actuator server ("motion appliance"). Stable external
  contract. Bounded latency. Deterministic safety. The Pi tells it *what* to do;
  it owns *how* and *when* the motor actually moves.
- **Raspberry Pi** = supervisory client / robot brain. Computes intent,
  coordinates multi-wheel commands, runs the GUI. Treats the STM32 as a service
  endpoint.
- **Contract**: The UART protocol is the service API. Commands are requests;
  responses are acknowledgments. The heartbeat watchdog is the liveness guarantee.
  The E-STOP latch is the safety invariant.

This reframing changes the priority of every finding in this thread.

## What the root cause resolution means

The 11:30 entry closed the connection failure: empty-line probe → firmware
produces zero response → client times out. Fix: probe with `PING 0`. This is
**correct and complete** for the immediate symptom.

But the root cause also exposes a design principle: the firmware's command
protocol is strict-in, strict-out. If you send garbage, you get silence. This
is actually *correct behavior for a safety-critical motion service* — better to
ignore than to misinterpret. The client was at fault for assuming an empty line
would provoke a response. The fix aligns client behavior with the firmware's
actual contract.

## Remaining findings re-evaluated through the service lens

### P0 (contract violation): CommsTask 10ms poll

The 10ms `vTaskDelayUntil` in `comms_task.cpp` is not merely a "nice to fix"
optimization. For a real-time motion service:

- **Bounded latency** is a requirement, not a wish. If the Pi sends a
  coordinated multi-axis command (e.g., "all four wheels start simultaneously"),
  each STM32 adds 0-10ms of random jitter *before it even begins parsing the
  command*. Over 4 wheels, this means up to 40ms of desynchronization — visible
  as jerky starts and stops.
- **Heartbeat accuracy** suffers: the watchdog timeout must be set ≥10ms above
  the actual heartbeat interval to absorb the poll jitter, reducing the
  resolution of liveness detection.
- **Fix**: ISR-driven task notification on `\n` receipt in `uart_transport.cpp`.
  The `USART2_IRQHandler` already fills the ring buffer; add
  `xTaskNotifyFromISR(commsTaskHandle, ...)` when the received byte is `\n`.
  `vCommsTask` replaces `vTaskDelayUntil` with `xTaskNotifyWait` (with the
  10ms as a fallback timeout for telemetry publishing). Command latency drops
  from 0-10ms to <100µs.

### P1: Worker thread serialization (client-side jitter)

`serial_worker.py` processes one operation per 10ms loop tick. If a heartbeat
is in-flight when a motion command arrives, the command waits. For a
coordinated multi-wheel system, this client-side jitter compounds with the
firmware-side jitter above.

Mitigation options (in order of invasiveness):
1. **Priority queue**: user commands jump ahead of heartbeat/telemetry
2. **Separate heartbeat channel**: dedicated thread or async I/O for heartbeats
3. **Batch commands**: group motion commands that must be synchronized

### P1: Character echo in machine mode

Echo exists for human terminal debugging. A machine client (the Pi) doesn't
need it. In JSON mode, echo adds ~1ms of blocking TX per command, and the
client must skip echo lines in every response. The firmware should suppress
echo when `ResponseFormat == JSON`.

### P2: SPI bit-bang critical sections (future)

When LCD rendering is re-enabled, the shared SPI bus with `taskENTER_CRITICAL`
per byte will cause UART byte loss under load. This is a ticking time bomb for
a system that needs to maintain comms reliability while rendering status
displays. Plan: either (a) hardware SPI with DMA, or (b) dedicated SPI bus
per device.
